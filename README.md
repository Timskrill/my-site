# My Site

Моя визитка с автоматическим CI/CD через GitHub Actions.

**Сайт:** https://timskrill.github.io/my-site/

**Репозиторий:** https://github.com/Timskrill/my-site

---

## Что делает пайплайн

Файл `.github/workflows/ci-cd.yml` описывает два задания:

1. **CI (Lint & Test)** — при каждом push или pull request в ветку `main`:
   - устанавливает зависимости (`npm install`)
   - запускает линтер HTML (`npm run lint`)
   - запускает тесты (`npm test`)
   - собирает продакшен-версию в папку `dist/` (`npm run build`)
   - загружает `dist/` как артефакт `site-build`

2. **CD (Deploy to GitHub Pages)** — только после успешного CI и только при push в `main`:
   - скачивает артефакт `site-build`
   - публикует его на GitHub Pages

## Ответы на вопросы

### Чем отличается CI от CD?

**CI (Continuous Integration, непрерывная интеграция)** — это автоматическая проверка кода при каждом коммите. В нашем пайплайне CI выполняет: установку зависимостей, линтер, тесты и сборку. Цель CI — как можно раньше обнаружить ошибки и не пропустить сломанный код в основную ветку.

**CD (Continuous Delivery / Deployment, непрерывная доставка или развёртывание)** — это автоматическая публикация собранного артефакта в продакшен. В нашем случае CD публикует папку `dist/` на GitHub Pages. Цель CD — быстро и без ручных действий доставить проверенный код до пользователя.

Ключевое различие: CI отвечает за качество кода, CD отвечает за доставку результата.

### Что произойдёт, если тесты завершатся ошибкой на этапе CI?

Пайплайн остановится на упавшем шаге. Все последующие шаги текущей задачи будут пропущены. Задача deploy вообще не запустится, потому что в ней стоит `needs: ci` — она ждёт успешного завершения CI. В итоге сломанный код не попадёт на продакшен.

Это хорошо видно в эксперименте №2: после изменения `test` на `exit 1` шаг Run tests упал, шаги Build и Upload artifact были пропущены, а задача Deploy to GitHub Pages не появилась.

### Для чего используется директива `needs: ci` в задаче развёртывания?

`needs: ci` создаёт зависимость между задачами. Задача `deploy` запустится только после того, как задача `ci` успешно завершится. Если CI упал или был отменён — deploy не выполнится.

Это защищает продакшен от публикации нерабочего кода. Без `needs: ci` обе задачи запускались бы параллельно, и deploy мог бы опубликовать сломанный сайт.

### Что такое артефакт и для чего он передаётся между задачами?

**Артефакт** — это набор файлов, который одна задача сохраняет для дальнейшего использования другими задачами или для скачивания вручную.

В нашем пайплайне:
- Задача `ci` собирает папку `dist/` (готовый сайт: HTML, CSS, JS) и загружает её как артефакт `site-build` через `actions/upload-artifact@v4`.
- Задача `deploy` скачивает этот артефакт через `actions/download-artifact@v4` и публикует содержимое на GitHub Pages.

Передача через артефакт нужна потому, что задачи `ci` и `deploy` выполняются на разных виртуальных машинах (разных runner'ах). Они не видят файлы друг друга напрямую. Артефакт служит промежуточным хранилищем, через которое файлы передаются из одной задачи в другую.
